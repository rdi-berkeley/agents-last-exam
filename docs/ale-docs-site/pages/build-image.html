Build a custom image

ALE boots each sandbox from a named image. The published ale-ubuntu22 and ale-win10 images already carry the software the public task set needs. Build your own when you add a task that wants software not yet baked in, or when you provision licensed Windows applications that the public images omit. The steps below use the Google Cloud provider throughout; other providers follow the same build-then-snapshot shape.

When you do not need this
The published images cover every task in selected_tasks/unlicensed.txt. Copy them as-is from the Google Cloud quick start and skip this page unless you are adding software or enabling licensed tasks.

The image model

An ALE image is a boot disk with three things baked in: the CUA server and its runtime (node, a framework Python), the system software tasks call out to, and — under task_data_source: baked_in_sandbox — the task data itself. Each image is described to the framework by one small module under ale_run/environments/images/ that records the VM-side paths the deployer relies on without discovery, and is referenced from an environment config by its registry name. 

# ale_run/environments/images/ale_ubuntu22.py
IMAGE = Image(
    name="ale-ubuntu22",                 # the name an environment config selects
    os="linux",
    work_dir_base="/home/user/.ale",     # per-run scratch
    task_data_root="/media/user/data/agenthle",
    node="/usr/local/bin/node",
    python="/opt/ale-run/.venv/bin/python",
    mcp_server_dir="/home/user/cua_mcp_server",
    default_machine_type="e2-standard-4",
    cua_server_port=5000,
)

These fields are read dynamically wherever the framework needs them — nothing is hard-coded, so a custom image sets its own port and paths. The only constraint is that each value is real: the image must actually run the CUA server on the declared port, and the paths must exist and be writable. Building an image is therefore two things: install the software and data, and declare where they live in the module.

published base image (ale-ubuntu22 / ale-win10) └── boot a builder VM └── install system packages (env/install_task_deps.sh) └── verify (env/verify_task_env.sh) └── bake task data (optional: input/ + reference.7z) └── snapshot disk → new named GCE image └── register the family + point an environment at it

The per-task package system

Every task declares the system software it needs in its task_card.json: 

"requiredSystemPackages": ["energyplus-22.1.0", "docker-ce"]

Each id maps to one idempotent installer in the package library under env/ — there are no per-task build scripts:

  • env/packages-linux/<id>/ — install.sh + meta.json (Linux).
  • env/packages-win/<id>/ — install.ps1 + meta.json (Windows Server 2022).

Installers provide only system software and libraries — apt packages, version-pinned /opt (Linux) or C:\Softwares (Windows) binaries, docker images. They do not install task Python packages (see the Pythons below). Version-pinned tools install to a versioned path so multiple versions coexist, and a task's software/ wrappers exec those exact paths.

Two entry points drive the library from a task card:

# install every requiredSystemPackages id, in order
env/install_task_deps.sh path/to/task_card.json

# run each package's meta.json "verify" command, and — if a task base dir is
# given — build its input/runtime_env with uv to prove the pinned Python
# runtime resolves against the freshly installed system libraries
env/verify_task_env.sh path/to/task_card.json path/to/task_base_dir

Run install_task_deps.sh for each task card you want the image to cover; installers are idempotent, so the image converges to a superset. Full policy: env/README.md.

The Pythons (what the image owns, what it doesn't)

Python in ALE spans three interpreters with three owners. The image bakes only one of them.

InterpreterWhere it runsResponsible forIn the image?
Host framework venv The ALE host, outside any sandbox. The orchestrator, and loading each task module to read its config and hold its evaluate() function. A grader's import-time dependencies must resolve here. No — host setup, never baked.
Image python Inside the sandbox (Linux /opt/ale-run/.venv, Windows system Python). The in-sandbox framework entry point and agent hosting. install_agent_deps() pip-installs each agent's declared packages into this interpreter at launch. Yes — this is the python field your module declares.
Per-task runtime Inside the sandbox, per task. Running the scoring scripts that evaluate() dispatches onto the VM with session.run_command. Today the tasks that isolate their own runtime ship a baked reference/evaluator_env/.venv (inside reference.7z) that their main.py names explicitly; an input/runtime_env/ (uv --frozen) is also supported but not yet used by any shipped task. Tasks with neither fall back to the image's Python. Baked into the task data, not the OS image's python.

The one you bake is the image python: keep it user-writable and minimal — pydantic, pip, and what install_agent_deps() adds — not a home for task libraries.

Recommended split when you build your own
Keep the image python minimal; pin every task's score-time deps in its own baked input/runtime_env/ (uv --frozen, which verify_task_env.sh builds); keep the host venv complete for graders. Today this is uneven — a few tasks isolate their runtime in an evaluator_env venv, most lean on the image Python.

1. Boot a builder VM

Start from the matching published base so the CUA server, node, Python, and path conventions are already in place. Create a VM from the base image and keep it running while you install software: 

gcloud compute instances create ale-builder \
  --image=ale-ubuntu22 --image-project="$GCP_PROJECT" \
  --machine-type=e2-standard-4 \
  --zone="$GCP_REGION-a" \
  --tags=ale-run

For a Windows image, build from ale-win10 (or ale-win-server for the GPU family) over RDP.

2. Install and verify the software

Copy the env/ tree to the builder and run the installers for each task card you want the image to cover. On Linux: 

# on the builder VM, repo root
for t in $(grep -v '^#' selected_tasks/linux_only.txt); do
  sudo env/install_task_deps.sh "tasks/$t/task_card.json"
done

# verify each package self-checks and the task runtimes resolve
env/verify_task_env.sh tasks/<domain>/<task>/task_card.json \
                       tasks/<domain>/<task>

On Windows, run the per-package install.ps1 from an elevated PowerShell, then confirm each meta.json verify command returns true. Installers pin exact versions on purpose: some graders reject the wrong build (for example the Blender task accepts 5.0.x and rejects 4.5.x), so do not float versions.

3. Bake task data (optional)

With task_data_source: baked_in_sandbox the task data lives on the image rather than being staged at run time. The convention under the image's task_data_root is: 

<task_data_root>/<domain>/<task>/<variant>/
├── input/            ← visible to the agent from stage_inputs onward
└── reference.7z      ← password-encrypted; decrypted to reference/ at grading

The reference archive stays encrypted during the run and is decrypted only at grading. Both images carry 7z on PATH. To skip baking, point the environment at a gs:// source instead — see Run and collect results.

4. Snapshot the disk into a named image

Stop the builder, then create a GCE image from its boot disk. Deleting the instance with --keep-disks=boot leaves the disk in place to image from: 

gcloud compute instances stop ale-builder --zone="$GCP_REGION-a"
gcloud compute instances delete ale-builder --zone="$GCP_REGION-a" \
  --keep-disks=boot

gcloud compute images create ale-ubuntu22-custom \
  --source-disk=ale-builder --source-disk-zone="$GCP_REGION-a"

To share the image with other projects, copy it the same way the quick start copies the published images: 

gcloud compute images create ale-ubuntu22-custom \
  --source-image=ale-ubuntu22-custom \
  --source-image-project="$GCP_PROJECT"

5. Register and select the image

If you reused the base image's name, you are done — environments already point at it. To ship a new family, add a module under ale_run/environments/images/ declaring its IMAGE = Image(...) (copy the closest existing module and adjust name and any paths), register it in the package _REGISTRY, then select it from an environment config by name: 

snapshots:
  cpu-free-ubuntu:
    provider: gcloud
    image: ale-ubuntu22-custom    # ← your registered image name
    gcloud:
      project: ${env:GCP_PROJECT}
      service_account_key: ${env:GCP_SA_KEY}
      instance_prefix: ale
      network: ale-vpc
      subnet: ale-vpc
      zones: [us-central1-a, us-east1-b, us-west1-a]

Validate with a one-task dry run, then a real run:

uv run python -m ale_run run my_experiment.yaml --dry-run
uv run python -m ale_run run my_experiment.yaml

If you changed cua_server_port, open that port in the firewall before running — ALE reaches the CUA server over TCP on it, and the Google Cloud setup only opens tcp:5000 (rule ale-allow-cua). A custom port needs its own ingress rule or the run is blocked: 

gcloud compute firewall-rules create ale-allow-cua-8000 \
  --network=ale-vpc --direction=INGRESS --allow=tcp:8000 \
  --source-ranges="$ALE_CLIENT_CIDR" --target-tags=ale-run

Licensed tasks

The public task set splits into an unlicensed subset that the published images run as-is, and a small licensed subset whose software cannot be redistributed. Of the 152 tasks in selected_tasks/full.txt, 145 are in unlicensed.txt; the remaining 7 are listed in selected_tasks/licensed.txt. Every licensed task today is a Windows task — there are no licensed Linux packages.

Their installers and credentials are not committed to the repository; keep them outside it. Each licensed package carries a meta.json (pinned version + verify command) and a README.md with one reproducible provisioning sequence (for example env/packages-win/rhino-8/):

  1. Purchase the product entitlement from the vendor.
  2. Assign the entitlement to the account used for installation.
  3. Sign in to the vendor account and download the pinned installer.
  4. Install and activate on the builder Windows VM, and disable automatic updates to preserve the pinned build.
  5. Run the package's meta.json verify command.

Provision the licensed software into your Windows builder alongside the unlicensed software — one image carries both — then snapshot and register it like any other custom image (steps 4–5). Point your Windows snapshot at that image and run selected_tasks/licensed.txt.

Checklist

  • Booted a builder from the matching published base image.
  • Ran install_task_deps.sh for every target task card and confirmed verify_task_env.sh passes.
  • Baked task data (or chose a gs:// source).
  • Stopped the builder, kept its boot disk, and created the named image.
  • Registered the family (only for a new name) and pointed an environment at it.
  • Validated with a one-task dry run, then a real run.
