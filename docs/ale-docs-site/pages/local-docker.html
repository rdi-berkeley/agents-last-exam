Local containers

Run the supported Ubuntu subset as one fresh Docker container per run unit. This is the lightest local provider, but it is not a full virtual machine and does not support Windows tasks.

Supported Linux subset
Use configs/environments/docker.yaml with selected_tasks/docker_support.txt for 102 v1.1 tasks, including Blender building reconstruction, MuseScore transcription, and Ardour project migration. Use the matching runtime digest and data pins.

What runs where

The shipped profile pins the v1.1 image by registry digest. See releases/v1.1/assets.json for exact versions and checksums.

The docker provider starts agentslastexam/ale-ubuntu22-docker:v1.1. The image is an export of the ale-ubuntu22 VM userspace, including its applications, Python environment, Node runtime, CUA server, and filesystem paths. A virtual X display provides the desktop surface.

The task runs directly in the container and shares the host kernel. Use the QEMU/KVM VM provider when a complete guest operating system or Windows is required.

Host requirements

  • Docker capable of running Linux amd64 containers. The supported profile targets rootless Docker on a Linux host.
  • Persistent disk space for the pinned runtime, data archive, its extracted contents and per-run files.
  • Enough CPU and memory for each concurrent task container.
  • Approved access to the gated task-data dataset on Hugging Face.

df -h .
uv sync --all-packages

Fetch task data once

The container image intentionally ships without task inputs or references. Request access to the ALE task-data archive, authenticate with Hugging Face, then run: 

huggingface-cli login
REVISION=$(jq -r '.huggingface.archive.revision' releases/v1.1/assets.json)
SHA256=$(jq -r '.task_data.archive_sha256' releases/v1.1/assets.json)
scripts/fetch_task_data.sh --revision "$REVISION" --sha256 "$SHA256"

The script verifies the immutable revision and checksum, then extracts into a new or empty ./task-data-v1.1 directory. Before the agent runs, ALE copies input/ and software/ into the container. It copies reference/ only after the agent finishes.

Use the shipped environment

environment: configs/environments/docker.yaml
tasks: selected_tasks/docker_support.txt

The environment uses task_data_source: local:task-data-v1.1. Keep output_path: null for benchmark runs and inspect artifacts in sandboxes retained with cleanup_mode: keep; release them after inspection. Run metadata, trajectories, evaluations, and telemetry are still collected. Set output_path: local only when bulk output collection is needed. Local task data and collected output use host-side docker cp, avoiding per-file transfer through the CUA API.

Resource sizing

By default the provider translates each task card's GCE machineType into Docker CPU and memory limits. The schema also accepts explicit vm.vcpus and vm.memory_gb values. Set docker.cpus or docker.memory in a copied environment profile to impose a provider-level cap.

Output options

The optional local path copies produced files into the run directory. GCS output is also supported when gcs_sa_key and a gs:// output path are configured. See Choose where task output goes.

Current limits

  • Linux tasks only. Windows and GPU snapshots are not mapped.
  • The sandbox shares the host kernel and is not VM-isolated.
  • Nine Linux tasks are excluded: four require nested Docker, two require Apptainer or Singularity GUI bundles, and three require namespace or systemd/cgroup facilities unavailable in the default profile.
  • G-code requires bubblewrap PID/network namespaces, which the default container denies. Road and inner-support require systemd supervision, while the entrypoint runs the CUA server as PID 1. Inner-support also requires writable delegated cgroups; the container mounts cgroups read-only. AppImage extraction fixes only FreeCAD launching, not these evaluator requirements.
  • Use the QEMU/KVM VM provider for these excluded tasks, preserving their isolation and resource limits.
  • Opt-in privileged DinD hooks remain available for custom development setups, but they are not part of the supported default task list and can add substantial I/O at high concurrency.
